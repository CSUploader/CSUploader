# Avalonia Migration Phase 6: Hard Views — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Avalonia head's three hardest views real — **UploadsView** (custom column-header re-template with lock toggle + resize grippers, ~40-item context menu, progress MultiBinding cell, editable Order column, package-expanding copy, durable filtered collection view, JD2 overview panel), **SettingsView** (ListBox sidebar + four DataTrigger-switched panels, a READ-ONLY accounts grid with a storage MultiBinding, an EDITABLE proxies grid, font enumeration), and **UploadWizardWindow** (4-step wizard, custom Expander re-template, two grids, a DatePicker across a `DateTime`↔`DateTimeOffset?` mismatch, two-way EnumBool RadioButton groups) — with the **Uploads and Settings MainWindow tabs going live** and the wizard opening from the Uploads toolbar. After this phase the app is feature-complete on Avalonia except Phase 7 shell behaviors (toasts, tray, dark-title-bar) and Phase 8 WebView login. Every view is verified by headless interaction tests plus WPF-vs-Avalonia reference shots in the phase contact sheet.

**Architecture:** Strangler step 6 (`docs/superpowers/specs/2026-07-10-avalonia-migration-design.md`, §Phases "Phase 6"). The design's Phase 6 line carries **10 PREP ITEMS** from the Phase 5 gate; every one is a task, an explicit step, or a port-rule row here (§Prep-item coverage). The three views are individually larger/riskier than anything in Phase 5, so **probe-first discipline is mandatory** — Task 1 is the column-header re-template GO/NO-GO probe (mirrors Phase 5's grouping probe), and the DatePicker + Expander arbitrations happen in the gallery (Task 2) BEFORE their consuming steps are ported. **The Core ViewModels are read-only this phase** — UploadsViewModel, SettingsViewModel, ConnectionManagerViewModel, UploadWizardViewModel and FileHosterSelectionViewModel were purified in Phase 1 and already expose everything the views bind. If a port seems to need a VM change, STOP and surface it to the team lead. Core's `InternalsVisibleTo("CSUploader.Avalonia")` (Phase 5 Task 3) already lets the head read `UploadsViewModel.SettingRepo`/`DialogServiceForView`; **Core is untouched this phase.**

**Tech Stack:** unchanged — .NET 10, Avalonia **11.3.18** + Avalonia.Controls.DataGrid **11.3.13** + Avalonia.Themes.Fluent + Avalonia.Svg.Skia 11.3.0, Avalonia.Headless.XUnit 11.3.18, CommunityToolkit.Mvvm 8.4.2 (Core). **This phase adds NO packages.** Bridge via `scripts/ava-drive.cs`; contact sheet via `scripts/contact-sheet.py`.
