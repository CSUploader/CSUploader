## Highlights

**Uploads use every connection a host allows, at the speed you actually asked for.** Five hosters now
send a file's parts in parallel instead of one after another, and the speed limit — which was quietly
multiplying itself across concurrent uploads — became a single shared budget. The updater also stopped
being a rectangle that sits still: it tells you how much has arrived, how fast, and how much longer.

## The speed limit was per hoster, not per upload

If you set a 1 MB/s cap and four chunks were in flight, each of them got the full 1 MB/s. The app
uploaded at four times the limit you set. Measured, before the fix: **394 kB/s against a configured
100 kB/s**.

The limit is one shared token bucket per scope now. Everything governed by the same limit draws from
the same budget, so the total is the number you set no matter how many connections are open. It
accrues continuously rather than in fixed windows, which is what stops a limit from stalling and then
bursting, and the bucket holds a tenth of a second's worth — so over any window longer than a moment
the rate is what you asked for.

Per-package and per-file overrides still behave as they always did: an override **may exceed** the
global limit. That is deliberate and unchanged — it is what an override is for.

**MEGA and transfer.it were ignoring the speed limit entirely.** Not partially: completely. Those two
encrypt the file themselves and write ciphertext straight to a WebSocket, so they never touch the
layer every other hoster is throttled in. They obey it now, paced in fragments rather than whole
chunks — a 1 MiB chunk charged up front would have waited ten seconds at 100 kB/s and then burst a
megabyte, which defeats the point of a limit, and at very low limits the wait alone outlasted the idle
watchdog and killed healthy uploads.

## Parallel part uploads

**VikingFile, Hostize, DataNodes, UploadNow and storage.to** send a file's parts concurrently.

A benchmark against VikingFile confirmed this was worth doing before any of it was written: that host
throttles **per connection**, so eight parts ran **2.57×** faster than one, and it had not plateaued
at eight. Hosts that throttle per account rather than per connection will not speed up, which is why
each hoster declares whether it supports this rather than the app assuming.

**Settings → Upload → Max parallel parts per file** caps it, default **4**. Set it to 1 and every
hoster behaves exactly as it did before this release. The cap is per file, so five files uploading at
once with a cap of 4 means up to 20 connections.

Two things worth knowing:

- **Progress is aggregated, not per part.** The bar is one monotonic total for the file, which is
  harder than it sounds when parts complete out of order and report their own offsets.
- **The first failure wins by part number, not by timing.** If parts 2 and 5 both fail, you are told
  about part 2 — the earliest problem, not whichever thread reached the error handler first.

## The update window says how fast, how much and how long

Updating showed a bar and a percentage. Now it also shows bytes received of the total, the rate, and
the time remaining.

There is a limitation worth stating plainly, because you will see it: **when the update is applied as
a delta, there are no byte figures — only the bar, the percentage and the countdown.** This is
deliberate. The updater reports a single percentage for the whole operation, and on the delta path
that operation downloads several deltas *concurrently* and then spends its last stretch patching,
which moves no bytes at all. The same percentage can correspond to many different byte totals, and no
arithmetic recovers which. A first attempt derived them anyway and was wrong; showing nothing is
better than showing a confident wrong number. Full downloads show everything.

The countdown survives on both paths because it is derived from the *percentage* rate rather than the
byte rate — the one design choice that keeps working when there is no size to count against.

## Fixed

- **A failed multipart upload left its parts on the host's storage forever.** Every retry started a
  fresh upload and abandoned another set, and nothing ever collected them: an incomplete multipart is
  invisible to the account's file list and to the site's own UI. UploadNow is the only one of the five
  that exposes a way to clean this up, and it now does — on its own bounded timeout, since the usual
  reason to be cleaning up is that the upload was cancelled.
- **UploadNow could report a failed upload as a finished one.** Its storage can return an error inside
  an HTTP 200, and the check for that matched a literal `<Error>` — while the real responses are
  namespaced, and walked straight past it. A truncated or empty response did the same. The result was
  a file presented as online that the storage had never assembled.
- **DataNodes could finalise a file with a missing chunk.** Its acceptance check looked for the text
  `"status"` and `"OK"` anywhere in the response, so `{"status":"NOT OK"}` counted as success.
- **The wizard's Account dropdown stopped short of its column's right edge**, reported by a user on
  Linux and reproducing on Windows too. It carried an 8px right inset that quietly defeated the
  stretch it was supposed to have.
- **The wizard summary bar quoted size caps in the wrong units.** DropMB's row said 500 MB while the
  bar underneath said 476.84 MiB for the same cap.

## Notes

- All new strings are localized in the usual six languages.
- **Set "Max parallel parts per file" to 1 to get exactly the previous upload behaviour**, if you
  would rather wait for field reports before letting the app open several connections per file.
- No hoster verdicts, size caps or retention figures changed in this release.
