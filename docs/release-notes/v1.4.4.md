## Highlights

**A hoster's size cap now reads the way the hoster itself writes it.** The wizard's "Max file size"
column used to render every cap in binary units, which quietly put the app at odds with the hosts it
was quoting: DropMB's cell said **488.28 MiB** where its site — and its own `/api/configs` — say
**512 MB**. Both are the same 512,000,000 bytes, but only one of them is the number you can go and
check. A user reported exactly that cell, and this release fixes it.

## What changed

- **Declared caps render in whichever base the figure is round in.** DropMB's 512,000,000 bytes now
  read "512 MB"; 1Fichier's 5 GB no longer shows as "4.66 GiB". Hosts that genuinely think in binary
  are untouched — DropMeFiles' 53,687,091,200-byte cap still reads "50 GiB", because that is the
  round one there.
- **The rule is roundness, not a per-host table.** Whichever base renders the count cleanly — a
  whole number, or exactly one decimal — at its largest applicable unit wins; binary takes ties and
  anything clean in neither. So "512 MB" and "5.5 GB" qualify where "488.28 MiB" doesn't, and no
  hoster needs its units hand-maintained as its cap changes.
- **All three surfaces that quote a declared cap moved together** — the wizard column, the step-2
  oversize warning, and the queue-skip line in the log. A test pins the column and the warning to
  the same string, so the app can't tell you "512 MB" in one place and "488.28 MiB" in another for
  the same cap.

## What deliberately did not change

**Measured quantities keep their explicit bases** — file sizes, transfer progress, storage figures,
speeds. A cap is somebody's *advertised* figure and should be quoted as advertised; a measurement is
nobody's, and letting it pick a base by roundness would make the units flap as the number moves
(a transfer ticking past 999 MB would jump between systems mid-upload). Per-pipeline fail-fast
messages still use their own wording and are left for a later pass.

## Notes

- This is a display fix only. No cap moved, no upload behaviour changed — the same files were
  accepted and rejected before and after.
- Verified against DropMB's live `GET /api/configs` (`share.maxSize=512000000`) rather than its
  marketing copy.
